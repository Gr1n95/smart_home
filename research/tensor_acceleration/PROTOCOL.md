# Протокол воспроизводимого сравнения CPU Raspberry Pi 5 и тензорного ускорителя

**Статус:** предварительно зарегистрированная методика; **данных Pi 5 ещё нет**. Этот документ фиксирует определения и условия до просмотра результатов. Не переносить в таблицы времена из `docs/01c_CORAL_INTEGRATION.md` — они не измерены. См. [рукопись](../../docs/16_TENSOR_ACCELERATION_MANUSCRIPT.md).

## 1. Проверяемый вопрос и границы вывода

Парное сравнение **каждой конкретной INT8-модели** на CPU одного Pi 5 и в её компиляции для подключённого Coral M.2. **Основной прикладной исход** для детектора — задержка полного пути «декодированный кадр → подготовка → детектор → боксы» на одинаковых кадрах с контролем качества. Энергопотребление и USB-сравнение не входят в эксперимент: измерителя мощности и USB-ускорителя нет. Время `invoke()` и `set+invoke+get`, батч `1`, являются *диагностическими* исходами, объясняющими устройство выигрыша, а не заменой замера полного пути. Имеющийся `benchmark.py` собирает только диагностические исходы: полный конвейер ещё предстоит реализовать и проверить. Результаты относятся только к Pi 5, конкретному Coral, версиям ПО, выбранным моделям и данным; общие принципы из главы 1 не делают эти числа универсальными.

Гипотезы H1–H3 и математические допущения находятся в рукописи. Первое сравнение **внутри одной пары моделей**, второе — связь выигрыша с нагрузкой **между парами** с оговоркой об архитектуре и размере входа. Измерение на синтетических входах не является оценкой качества и не должно называться скоростью детектора на естественных кадрах.

## 2. Замораживаемые условия и сведения о стенде

Перед каждым запуском записать в журнал: модель/ревизию Pi 5 и объём ОЗУ, M.2-адаптер, способ питания и охлаждения, ОС/ядро, CPU governor, драйвер `gasket/apex`, путь устройства `/dev/apex_0`, `libedgetpu`, версии `tflite_runtime`/PyCoral/NumPy, число CPU-потоков, фоновую нагрузку и состояние Throttling. Зафиксировать SHA-256 каждого `.tflite`, seed и версию кода (Git commit). Аппаратные версии/температуру нельзя заменять названием «Raspberry Pi 5» в подписи таблицы.

Пары для первого опыта доступны в [официальном дереве тестовых моделей на коммите 104342d](https://github.com/google-coral/test_data/tree/104342d2d3480b3e66203073dac24f4e2dbb4c41):

| CPU-модель `.tflite` | Суффикс парной версии | Роль |
|---|---|---|
| `mobilenet_v1_0.25_128_quant` | `_edgetpu` | Малая классификация |
| `mobilenet_v1_0.5_160_quant` | `_edgetpu` | Промежуточная нагрузка |
| `mobilenet_v1_0.75_192_quant` | `_edgetpu` | Промежуточная нагрузка |
| `mobilenet_v1_1.0_224_quant` | `_edgetpu` | Большая классификация |
| `ssd_mobilenet_v2_face_quant_postprocess` | `_edgetpu` | Детекция лиц и полный конвейер |

Загрузить исходный CPU-файл и парный TPU-файл из **одного снимка** источника, сохранить контрольные суммы. Проверить до замеров: форму/тип/квантование входов, совместимость и порядок выходов, делегирование (`edgetpu_compiler`/доступный отчёт) и наличие устройства. При компиляции CPU-модели самостоятельно версия и лог компилятора записываются отдельно: отчёт повторной компиляции **не обязательно** соответствует скачанному готовому `_edgetpu` файлу. Не запускать CPU float вместо CPU INT8. CPU-потоки основной серии фиксировать (например, 4), варианты 1/4 — отдельный фактор. В опубликованной реализации `pycoral.utils.edgetpu.make_interpreter()` нет параметра `num_threads` для CPU fallback: число потоков оставшихся на CPU операторов может не совпадать с заданным для CPU-контроля. Зафиксировать это как ограничение, отдельно сравнить CPU в 1 и 4 потока и не выдавать разницу за чистое время кристалла.

## 3. Входы и экспериментальный контроль

Для микробенчмарка заранее готовые одинаковые тензоры формы/типа входа сети. Основная публикационная серия должна использовать **реальные изображения**, одна реализация декодирования/resize/цвета/квантования для CPU и TPU. `.npy` массива формы `(N, *shape_одного_входа)` хранить локально, не коммитить изображения лиц. Синтетические входы допустимы для проверки инструмента и оценки вызова в искусственных условиях; пометить режим в логах, не делать выводов о прикладной точности. Для SSD возможна зависимость времени CPU-постобработки от содержания кадра, поэтому синтетика не заменяет реальную выборку.

Качество: независимые размеченные сцены, согласие на использование лиц; калибровочная часть — для порога уверенности, тестовая — только для финальной оценки. Для детектора `IoU ≥ 0,5`, однозначное сопоставление боксов с разметкой, `AP@0.5`, recall по условиям и FP на пустых кадрах. Для классификатора при наличии меток — top-1. Проверка численных расхождений выходных тензоров **не эквивалентна** этим метрикам.

Контроль температуры: основные опыты без Frigate/Whisper/других нагрузок на Pi; фоновый стресс — отдельная серия. Наблюдать частоту и температуру CPU; фиксировать перегрев, ошибки загрузки и прерывания. Нельзя молча удалять медленные кадры как «аномальные» после просмотра результатов. Время камеры и чтения измерять отдельно от прогретых входов; не объявлять `1000/t_invoke[мс]` реальным FPS камеры.

## 4. Порядок, размер выборки и сырые данные

1. Проверить модель и устройства; выполнить пилотную серию (предлагается ≥3 сессии × ≥5 блоков × ≥10 подготовленных входов), оценить вариабельность времени и требуемое число повторов. **Числа — первоначальное предложение, не анализ статистической мощности.** После пилота записать окончательное число сессий/входов/блоков и зафиксировать до основной серии.
2. В каждой сессии создать интерпретаторы один раз, зафиксировать время их создания/выделения отдельно и прогреть оба (например, по 50 вызовов). Не включать прогрев/чтение входных файлов в измерение инференса.
3. Для каждого блока чередовать порядок ABBA / BAAB; обе ветки получают одни и те же входы и проверяются на равенство размера/типа. На каждый вызов записать `(session, block, order, mode, input_id, t_set_ns, t_invoke_ns, t_get_ns, t_total_ns, temperature_mC, cpu_freq_kHz)` и сбои.
4. Вести первичный CSV **по каждому вызову**, JSON с конфигурацией стенда, SHA-256 и предупреждениями. Не оставлять в репозитории идентифицирующие изображения, эмбеддинги и большие модели; в PR публиковать только обезличенные сводные числа и скрипт.
5. Основной опыт дополнить парной прикладной серией с одинаковым декодированием, предобработкой и постобработкой детектора; **именно она** отвечает на вопрос о времени «кадр → боксы». До её реализации и проверки инструмент ниже измеряет **только** `set+invoke+get` и не является тестом полного пути.

## 5. Статистика и модель

Для основного кейса заранее зафиксировать метрику полного конвейера (например, медиана и p95 задержки от декодированного кадра до готовых боксов), IoU и правило подсчёта AP/recall, а также допустимое изменение качества. Не менять порог детекции на тестовой выборке ради ускорения. Содержание теперь ограничено двумя наблюдаемыми критериями — задержкой и качеством детекции; сохранение температуры/частоты CPU в журнале необходимо лишь для контроля условий.

- Вычислить для каждого режима и модели медиану и p95 в миллисекундах, число вызовов/входов/сессий и `S=median(t_CPU)/median(t_TPU)` отдельно для `invoke` и суммарного `set+invoke+get`.
- Для одного входа/блока парная разность `d=t_CPU−t_TPU` при согласованном порядке. Не считать тысячекратно повторённый один кадр тысячами независимых примеров качества.
- 95%-й интервал для ускорения и разности: блочный/кластерный бутстрэп по независимым сессиям, а для видео — по роликам/сценам; при малом числе независимых кластеров честно указать ненадёжность интервала вместо псевдоточного p-value.
- Для прикладной серии сравнить наблюдаемое `S_total` с прогнозом из измеренной неускоряемой части по закону Амдала; отделить параметры, измеренные непосредственно, от допущений о внутреннем времени TPU. Если имеется достаточно условий, оценивать параметры на одних условиях и проверять на отложенных. С тремя-пятью парами моделей **нельзя обосновать универсальную модель** для всех TPU.
- Не вычислять энергию из времени, частоты CPU или паспортных TOPS: измерителя мощности нет. Раздел ограничений должен прямо указать отсутствие измерений энергии.

## 6. Условия для ablation, контроля нагрева и профилировщика

- **Ablation.** Контраст A: одна архитектура и веса на CPU в float и INT8; контраст B: та же INT8-сеть на CPU и через TPU-делегат. Для контраста A нужны подтверждённые float-веса/процедура квантования; одни готовые INT8-файлы его не обеспечивают. Вклад отдельных неподдерживаемых операторов нельзя получить вычитанием общих времён A/B: нужны сопоставимые варианты графа и отчёты компилятора, иначе анализ fallback будет наблюдательным.
- **Тепловые условия.** Записывать доступные на Pi 5 температуру и частоту CPU, а также governor и состояние троттлинга в одинаковом режиме охлаждения. Значения относятся к CPU/плате, **не** к кристаллу Coral; они помогают исключить ложное ускорение из-за различий частот, но не являются измерением энергопотребления.
- **Визуализация делегирования.** Текущий микробенчмарк НЕ строит граф операторов. Для п. 2.7 разработать отдельный модуль разбора доступного отчёта компилятора и визуализацию сегментов CPU/TPU с подписью версии инструмента и недоступных сведений. Количество делегированных операторов не эквивалентно доле времени на TPU; без аппаратного профайлера не утверждать время отдельного слоя.
- **Интерфейс.** Coral M.2 подключён по PCIe. В опытах отсутствует USB-ускоритель, поэтому PCIe/USB не сравниваются. Учёт обмена с имеющимся устройством ведётся в модели задержки, а не в виде вымышленных бенчмарков другого интерфейса.

## 7. Микробенчмарк для первого сбора данных

`benchmark.py` **не требует** данных о лицах и не загружает модели из сети. На Pi 5 с установленными совместимыми `numpy`, `tflite_runtime`, `pycoral` и драйвером:

```bash
python3 research/tensor_acceleration/benchmark.py \
  --cpu-model /path/to/mobilenet_v1_0.25_128_quant.tflite \
  --tpu-model /path/to/mobilenet_v1_0.25_128_quant_edgetpu.tflite \
  --inputs-npy /private/prepared_128_inputs.npy \
  --output-dir research/tensor_acceleration/results/mobilenet_025_run1 \
  --threads 4 --sessions 3 --blocks 5 --warmup 50
```

Только для **технической проверки инструмента**, если подготовленных тензоров нет: заменить `--inputs-npy` на `--synthetic --num-inputs 10 --seed 2026`. Столбец/метаданные `synthetic=true` обязательны в этом случае; это не экспериментальная выборка. При отсутствии реального Coral программа должна **упасть с ошибкой**, а не незаметно включить CPU fallback вместо второго режима.

Результат: `runs.csv`, `manifest.json`, `output_comparison.json` в указанном каталоге. Расхождение выходных массивов записывается **вне тайминга**, но это не оценка точности по разметке. Каталог результатов игнорируется Git. Не заменять отсутствие этих файлов таблицами из прежнего диплома.
