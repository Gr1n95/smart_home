# Как работает тензорный ускоритель и какой выигрыш он даёт на Raspberry Pi 5

> **Новая основная программа конкурсного исследования.** Предмет — принципы вычислений в тензорных ускорителях и границы их эффективности по сравнению с CPU *того же* Raspberry Pi 5. Coral M.2 Edge TPU — доступный **экспериментальный образец**, а не сама «новизна». Полный конвейер детекции лиц — **основной прикладной кейс**; другие сети служат контролем влияния трудоёмкости. Тема не охватывает весь умный гараж. [Содержание работы по главам](./15_TENSOR_ACCELERATOR_CONTEST_OUTLINE.md). Измерений на реальном Pi 5 в репозитории пока нет.

## 1. Исследовательский вопрос

**Рабочее название:** «Принципы работы тензорных ускорителей и экспериментальная оценка их эффективности на примере полного конвейера детекции лиц на Raspberry Pi 5».

**Объект:** исполнение нейросетевых вычислений на периферийном устройстве. **Предмет:** связь между параллелизмом операций над тензорами, повторным использованием данных, квантованием, передачей данных и временем/энергией выполнения на CPU Pi 5 и подключённом ускорителе.

**Цель:** математически объяснить, за счёт чего специализированный ускоритель может исполнять некоторые нейросетевые операции быстрее CPU Raspberry Pi 5, и на реальном устройстве измерить, какой выигрыш получается **для модели и для полного конвейера детекции лиц** при контроле качества и, при наличии прибора, энергии. Не подменять эксперимент обещанием «ускорение в N раз».

**Гипотезы для проверки:**

1. На достаточно большой доле совместимых вычислительно насыщенных операций делегирование снижает задержку вызова модели относительно CPU Pi 5; для коротких/частично поддерживаемых графов результат может быть другим.
2. Выигрыш полного конвейера меньше выигрыша инференса, если чтение, предобработка, передача и постобработка занимают заметную долю времени.
3. Пиковые «TOPS» не позволяют предсказать задержку без сведений о размере задачи, обмене данными и CPU fallback.

Нулевая гипотеза для основной парной серии: медиана `t_CPU − t_ускоритель ≤ 0` при одинаковой квантованной модели и одних и тех же входах. Заранее определить, какие эффекты практически значимы и как проверять сохранность качества. **Научная составляющая** — не покупка Coral, а проверенная данными модель причин и границ ускорения; степень новизны согласовывается с правилами конкурса после получения результатов.

## 2. Как это работает: математическая и аппаратная модель

### 2.1. Тензорные операции и параллелизм

Для матричного умножения `C = A · B` с размерами `A ∈ R^(M×K)`, `B ∈ R^(K×N)`:

```text
C[i,j] = Σ_(k=1)^K A[i,k] · B[k,j];         MAC = M · N · K.
```

Разные выходные элементы можно вычислять параллельно, а считанные элементы `A` и `B` — использовать многократно. Например, блок результата `T_M × T_N` при проходе по `K` требует `T_M·T_N·K` MAC, а в идеализированной схеме с локальным хранением — чтения примерно `K(T_M+T_N)` входных элементов вместо `2T_M·T_N·K` чтений без повторного использования (запись результата и иерархия кэшей здесь опущены). Это иллюстрация *data reuse*, не описание реального числа транзакций Coral: оптимизированный CPU тоже применяет блокирование и кэширование.

Свёрточный слой также сводится к множеству скалярных произведений (явно или неявно без материализации `im2col`):

```text
y[i,j,o] = b[o] + Σ_(u,v,c) K[u,v,c,o] · x[i+u,j+v,c],
MAC_conv ≈ H_out · W_out · k² · C_in · C_out.
```

Для depthwise-свёртки с последующим `1×1` смешением каналов `MAC ≈ H_out · W_out · (k² · C_in + C_in · C_out)`. Например, при `H_out=W_out=128`, `k=3`, `C_in=32`, `C_out=64`: примерно `301 989 888` MAC для обычной свёртки и `38 273 024` для разделяемой — в `7,89` раза меньше **операций в этом примере**, но не обещание такого же прироста скорости.

CPU Pi 5 использует ядра общего назначения, кэши и векторные инструкции (SIMD/NEON); это **не** исключительно последовательный исполнитель. Типовые тензорные ускорители специализируются на параллельных умножениях с накоплением (MAC), конвейеризации и повторном использовании данных на кристалле. Систолический массив или блоковая матричная обработка — полезные **общие архитектурные модели**, но по ним нельзя без документации приписывать конкретную внутреннюю схему Coral. Корректный уровень объяснения для закрытого чипа: математическая операция → требования к параллелизму/памяти → наблюдаемое делегирование/время.

### 2.2. Память и предел производительности

Для оценки важны не только MAC, но и **операционная интенсивность** `I = O/Q`, где `O` — число операций, `Q` — объём перемещённых байтов **на явно указанном уровне памяти**. Оценка типа roofline:

```text
P_достижимая ≤ min(P_peak, B · I),
t_вычисления ≥ max(O/P_peak, Q/B),
```

где `B` — пропускная способность этого уровня. Повторное использование тензоров уменьшает `Q`; малая задача или частые обращения к внешней памяти дают слабый эффект даже при высокой пиковой производительности. Для подключённого к Pi 5 Coral добавить задержку вызова/драйвера и передачу данных по интерфейсу. Не подставлять паспортные TOPS вместо измеренной производительности; не смешивать число MAC с FLOP/OPS без оговорённой конвенции (часто 1 MAC учитывается как 2 операции).

### 2.3. Зачем квантование и что делает компилятор

Типичное аффинное отображение действительного числа в целый диапазон:

```text
q = clip(round(x/s)+z, q_min, q_max),      x ≈ s(q−z).
```

Здесь `s` — масштаб, `z` — нулевая точка. При выполнении поддерживаемых INT8-операций произведения накапливаются обычно в более широком целочисленном типе и затем переводятся к масштабу выхода. Квантование уменьшает объём представления и допускает специализированный целочисленный путь, но округление и насыщение могут влиять на результат. Эффект квантования **не равен** эффекту ускорителя: основной контроль — одна и та же INT8-модель на CPU и ускорителе; сравнение CPU float ↔ ускоритель INT8, если его проводить, сообщать отдельно.

Компилятор/делегат разбивает граф на выполняемые на ускорителе и оставшиеся на CPU операции. Неподдерживаемый слой, постобработка и обмен между сегментами могут съесть выигрыш. Суффикс `_edgetpu` в имени файла ещё не показывает, какая доля графа реально делегирована: нужен отчёт компиляции либо другая проверка графа, поддерживаемых операций и выходов. Точные ограничения и детали Coral следует брать из проверенной документации и проверять на конкретных версиях инструментов.

### 2.4. От времени к коэффициенту ускорения

```text
T_кадр = T_чтение + T_предобработка + T_ввод + T_invoke
       + T_вывод + T_постобработка.
T_invoke,ускоритель ≈ T_драйвер + T_передача + T_операции_ускорителя
                   + T_CPU_fallback.
S_invoke = median(T_invoke,CPU) / median(T_invoke,ускоритель),
S_кадр = median(T_кадр,CPU) / median(T_кадр,ускоритель).
```

Замер вокруг `invoke()` включает вызов с хоста, делегат и накладные расходы: он **не** измеряет отдельно время самого кристалла. Если `p` — доля исходного CPU-времени, которая действительно ускоряется в `a` раз, а `δ` — дополнительные накладные расходы в долях исходного времени, то приближённо по закону Амдала

```text
S_кадр ≈ 1 / ((1−p) + p/a + δ).
```

Иллюстрация, **не результат опыта**: при `p=0,6`, `a=10`, `δ=0,05` ускорение полного процесса `≈1,96`, а не `10`. Наблюдаемый выигрыш по времени появляется, только если сэкономленное время совместимых вычислений больше затрат на вызов, передачу и лишние CPU-переходы. При наличии внешнего ваттметра дополнительно измеряется `E = ∫ P(t)dt` на одинаковый объём работы; по времени или номинальной мощности **нельзя** достоверно вычислить энергию.

## 3. Как проверить это на Raspberry Pi 5

### 3.1. Сравнимые вычислительные задачи

В основной серии запускать на **одном и том же Raspberry Pi 5** каждую квантованную TFLite-модель в двух вариантах: CPU без TPU-делегата и её компиляцию с подключённым Coral M.2. Начальный набор кандидатов в [Coral `test_data` на фиксированном коммите](https://github.com/google-coral/test_data/tree/104342d2d3480b3e66203073dac24f4e2dbb4c41):

| Пара (исходный квантованный TFLite / `_edgetpu`) | Зачем |
|---|---|
| `mobilenet_v1_0.25_128_quant.tflite` | Относительно небольшая классификационная сеть: влияние накладных расходов. |
| `mobilenet_v1_1.0_224_quant.tflite` | Более тяжёлая классификационная сеть: проверка связи с объёмом MAC. |
| `ssd_mobilenet_v2_face_quant_postprocess.tflite` | Основной прикладной кейс: измерить CPU/TPU во всём пути обработки кадра и проверить качество детекции. |

Для каждой строки существует файл с суффиксом `_edgetpu.tflite` в том же снимке репозитория; **до опытов** проверить версии/хеши файлов, форму и тип входов/выходов, эквивалентность модели и долю делегированных операций. Это *предложение моделей для проверки*, не утверждение о работоспособности конкретного образа на имеющемся оборудовании. Сравнение **внутри каждой пары** изолирует влияние способа выполнения; сравнение времён между разными сетями без оговорок не является измерением «эффекта TPU». Если доступна только одна пара, честно сузить вывод до неё, а не обобщать на весь класс ускорителей.

### 3.2. Контроль и измерение

- Постоянные параметры: Pi 5, питание/охлаждение, версии ОС/драйвера/библиотек, число потоков CPU, размер батча `1`, входные тензоры, пороги обработки выходов; фиксировать SHA-256 моделей. Не запускать Frigate или другой потребитель TPU в основной серии; нагрузку изучать отдельно.
- На заранее загруженных одинаковых входах: прогреть интерпретаторы, чередовать CPU/TPU блоками и повторить независимые сессии, логировать `perf_counter_ns()` по этапам, ошибки, температуру и частоту CPU. Холодный старт (загрузка модели/инициализация) учитывать отдельно от установившейся задержки.
- В прикладной серии: одинаковые кадры детекции лиц, одна процедура преобразования и постобработки; раздельно замерить модель и **весь** путь «кадр → боксы». Разметка лиц (включая пустые и сложные кадры) нужна для `AP@0.5`, recall и частоты ложных срабатываний. Качество классификации при необходимости оценивать на одинаково размеченных изображениях, например top-1, отдельно от метрик детекции.
- Показатели: медиана, p95 и разброс времени, `S_invoke`, `S_кадр`, при подходящем приборе энергия на обработку одинакового числа входов, CPU fallback и доля неделегированных операций. Доверительные интервалы для видео считать по независимым сценам/сессиям, а не выдавать соседние кадры за независимые пробы. Приписывать изменение качества именно ускорителю можно только после контроля квантования и совпадения выхода моделей.
- Сопоставить измеренные ускорения с оценками по интенсивности операций и закону Амдала; указать, где модель не объясняет измерения. Если наблюдений недостаточно для количественного предсказания, сообщить только качественное объяснение, не «подгонять» закон под те же данные.

**Важно:** эксперимент позволяет сделать выводы о **конкретном** Coral и выбранных моделях на Pi 5. Принципы тензорных ускорителей объясняются в теории, но результаты нельзя автоматически переносить на любые TPU/NPU. Уточнять внутреннее устройство Coral сверх опубликованных сведений нельзя — это не исследование схемотехники закрытого чипа.
