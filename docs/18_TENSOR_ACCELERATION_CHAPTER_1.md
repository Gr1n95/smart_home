# 1 Анализ математических и архитектурных основ тензорных вычислений на edge-платформах

Оценка тензорного ускорителя требует различать три уровня: **математическую задачу** (какие операции выполняет сеть), **реализацию** (как данные размещаются и какие операторы исполняются на CPU и ускорителе) и **наблюдаемое время** обработки кадра. Одинаковое число арифметических операций не означает одинаковую задержку: результат зависит от движения данных, характера параллелизма, совместимости графа с устройством и затрат на обработку вне нейросети. В данном разделе рассматриваются аналитические оценки для этих уровней применительно к Raspberry Pi 5 и подключённому по PCIe Coral M.2. Числовые примеры иллюстрируют расчётные зависимости; экспериментальная оценка предусмотрена в разделе 2.

Обозначения используются в следующем смысле: `B` — число изображений в пакете; `H`, `W` — высота и ширина карты признаков; `C_in`, `C_out` — число входных и выходных каналов; `k_h`, `k_w` — размеры ядра свёртки. **MAC** (от англ. *multiply–accumulate*) — операция умножения с накоплением: `s ← s + a·b`. Например, выражение `2·3 + 4·5 = 26` вычисляется за два MAC при начальном `s=0`: сначала `s=6`, затем `s=26`. При подсчёте арифметических действий один MAC соответствует одному умножению и одному сложению, поэтому `N_ops ≈ 2 N_MAC`. Число MAC характеризует объём арифметики; задержка также зависит от организации памяти и способа исполнения.

## 1.1 Анализ выполнения тензорных операций в нейронных сетях и их вычислительной трудоёмкости

**Представление тензора.** В математике тензором называют объект, координаты которого преобразуются по определённому правилу при смене базиса. В машинном обучении термин обычно используют в прикладном смысле — для обозначения числового массива; именно это значение принято далее. Число осей массива называют его размерностью: скаляр содержит одно число и не имеет осей, вектор имеет одну ось, матрица — две.

При обработке пакета изображений удобно использовать массив с четырьмя осями `X[B,H,W,C]`: `B` — число изображений, `H` — высота в строках, `W` — ширина в столбцах, `C` — число каналов (например, три для изображения RGB). Такой порядок осей называют **NHWC**: буква `N` здесь обозначает ту же ось пакета, что и `B`. В этом же формате можно представить промежуточные карты признаков; для них `C` означает число каналов признаков. Форма массива (`shape`) перечисляет длины осей, а тип данных (`dtype`) задаёт представление каждого числа, например `int8` или `float32`. Всего массив содержит `B·H·W·C` элементов. Если каждый элемент занимает `b` байт и данные хранятся непрерывно, сами значения занимают `B·H·W·C·b` байт; служебные данные и выравнивание учитываются отдельно.

Пусть один кадр представлен массивом формы `(1,128,128,3)`. Он содержит `1·128·128·3 = 49 152` элемента. Если каждый элемент занимает один байт, массив требует не менее `49 152` байт; при 32-битном числе с плавающей точкой — `196 608` байт. Четырёхкратная разница в размере *представления* влияет на объём хранимых данных, а фактическая задержка зависит также от преобразования форматов, чтения других тензоров и выполнения операторов. Для оценки внутреннего трафика ускорителя необходимо учитывать реализацию вычислений.

Форма не задаёт расположение элементов в памяти полностью. При непрерывном NHWC-массиве смещение `X[b,h,w,c]` от начала в **элементах**, если индексы начинаются с нуля, равно `(((b·H+h)·W+w)·C+c)`. Для перевода в байты смещение умножают на размер элемента. В другой раскладке, например NCHW, соседние по адресу значения относятся к другим индексам. Представление с произвольными шагами (`strides`) вообще может быть неплотным: перестановка осей способна создать только представление без копирования, но следующий оператор может потребовать материализовать новый непрерывный массив. Поэтому стоимость изменения раскладки зависит от реализации, а не от того, что перестановка индексов математически выглядит «бесплатной».

Над массивами применяются поэлементные операции, редукции (сумма или максимум по оси), объединение и разбиение, изменение формы, матричное умножение и свёртки. **Поэлементная операция** обрабатывает каждую позицию отдельно; при сложении массивов формы `(H,W,C)` и `(1,1,C)` второй аргумент может распространяться по пространственным осям согласно правилу *broadcasting*. Такое «расширение» логически описывает один результат для каждой позиции, но не всегда требует физического повторения меньшего массива. **Редукция**, напротив, объединяет несколько входных значений в одно и обычно требует обмена промежуточными суммами. Стоимость обоих типов операций нельзя характеризовать только числом MAC: например, копирование или изменение формата может не содержать ни одного MAC, но занимать измеримое время.

**Матричное умножение как базовая форма вычисления.** Для `A` размера `M×K` и матрицы весов `V` размера `K×N` результат `Y=AV` имеет размер `M×N`. Каждый его элемент определяется скалярным произведением:

$$Y_{ij}=\sum_{k=0}^{K-1}A_{ik}V_{kj},\qquad 0\leq i<M,\quad 0\leq j<N.$$

Для одного элемента требуется `K` умножений с накоплением; для всего результата — `M·N·K` MAC. Скалярное произведение «сворачивает» общий индекс `k`, а элементы с разными `i,j` допускают параллельное вычисление. Например, при

$$A=\begin{pmatrix}1&2&-1\\0&3&4\end{pmatrix},\qquad V=\begin{pmatrix}2&1\\0&-2\\1&3\end{pmatrix}$$

получается `Y=((1,−6),(4,6))`: значение `Y₀₀=1·2+2·0+(−1)·1=1`, а `Y₀₁=1·1+2·(−2)+(−1)·3=−6`. Здесь всего `2·2·3=12` MAC. В современных сетях размеры могут быть больше на порядки, но способ организации вычислений остаётся тем же: одна и та же строка `A` участвует в формировании нескольких выходов, а один столбец `V` используется для разных строк входа. Эта возможность *повторно использовать* считанные данные является ключевой для быстрого исполнения.

Полносвязный слой нейросети записывается как `Y=AV+b`, где `b` — вектор из `N` смещений, одинаково добавляемый к каждой строке результата. Оценка `MNK` относится только к умножению, не включая сложение со смещением, функцию активации, выделение памяти и ввод/вывод. Для свёртки вычисление также можно представить как множество скалярных произведений между локальными участками входа и весами, хотя эффективная реализация не обязана строить в памяти полную матрицу этих участков.

**Свёртка пространственных карт признаков.** Для входа `X[B,H,W,C_in]` и тензора фильтров `F[k_h,k_w,C_in,C_out]` значение выходного канала `o` в точке `(i,j)` можно записать как

$$Y_{b,i,j,o}=\phi\!\left(\beta_o+\sum_{u=0}^{k_h-1}\sum_{v=0}^{k_w-1}\sum_{c=0}^{C_{in}-1}F_{u,v,c,o}\,X_{b,is_h+ud_h-p_h,js_w+vd_w-p_w,c}\right),$$

где `s` — шаг, `d` — разрежение ядра, `p` — дополнение нулями с каждой стороны, `β` — смещение, а `φ` — возможная функция активации. Значения входа за пределами карты считаются нулевыми. В библиотеках машинного обучения такая операция обычно реализует *взаимную корреляцию* без разворота ядра, хотя традиционно называется свёрткой. При симметричном дополнении высота выхода равна

$$H_{out}=\left\lfloor\frac{H+2p_h-d_h(k_h-1)-1}{s_h}\right\rfloor+1,$$

аналогично вычисляется `W_out`. Сначала нужно определить **фактические** размеры выходного тензора, и только потом оценивать работу слоя. Для стандартной свёртки число MAC составляет

$$N_{MAC,conv}=B\,H_{out}W_{out}\,C_{out}\,k_hk_wC_{in}.$$

Формула учитывает только умножения с накоплением; добавление смещения, активация и обработка рамок детектора относятся к другим операциям.

**Пошаговый пример для одного канала.** Пусть `X[1,3,3,1]` содержит одно изображение размером `3×3` с единственным каналом. Опуская две оси длины `1`, представим вход и один фильтр `2×2` как обычные матрицы:

$$X=\begin{pmatrix}1&2&0\\0&1&3\\2&0&1\end{pmatrix},\qquad F=\begin{pmatrix}1&0\\0&1\end{pmatrix}.$$

Фильтр сдвигается по изображению с шагом `1`, без дополнения нулями; разрежение равно `1`. Для наглядности смещение принимается равным нулю, а функция активации не изменяет результат. Фильтр можно разместить в четырёх положениях — сверху слева, сверху справа, снизу слева и снизу справа. В каждом положении соответствующие числа входа и фильтра перемножаются и складываются:

- **Сверху слева:** `1·1+2·0+0·0+1·1=2`.
- **Сверху справа:** `2·1+0·0+1·0+3·1=5`.
- **Снизу слева:** `0·1+1·0+2·0+0·1=0`.
- **Снизу справа:** `1·1+3·0+0·0+1·1=2`.

Получается выходная карта

$$Y=\begin{pmatrix}2&5\\0&2\end{pmatrix}.$$

Её форма — `[1,2,2,1]`: одно изображение, две строки, два столбца, один выходной канал. Для каждого из четырёх выходных значений плотная схема предусматривает `2·2·1=4` MAC, всего `4·4=16` MAC. Здесь учитываются и умножения на нулевые веса фильтра; конкретная реализация может их оптимизировать. Центральный элемент входа `X[0,1,1,0]=1` попадает во все четыре положения фильтра — так проявляется повторное использование данных.

**Пример с несколькими входными и выходными каналами.** Пусть вход `[1,8,8,3]` содержит изображение размером `8×8` с тремя каналами. Возьмём восемь фильтров размером `3×3×3`: каждый охватывает область `3×3` **во всех трёх каналах** и создаёт один выходной канал. При шаге `1`, разрежении `1` и дополнении по одному нулю с каждой стороны высота и ширина выхода сохраняются равными `8`. Поэтому форма результата — `[1,8,8,8]`: на каждой из `8·8=64` позиций вычисляется восемь выходных чисел. Для одного числа нужно `3·3·3=27` MAC, а для всей выходной карты — `1·8·8·8·27=13 824` MAC. В восьми фильтрах содержится `3·3·3·8=216` весов; одни и те же веса применяются ко всем пространственным положениям. В детекторе такие слои следуют друг за другом, а размеры и вычислительную трудоёмкость каждого слоя определяют по графу конкретной модели.

**Разделение свёртки на два этапа.** При обычной свёртке каждый выходной фильтр использует все `C_in` входных каналов. При групповой свёртке входные и выходные каналы делят на `g` групп: фильтр работает только с `C_in/g` каналами своей группы (если `C_in` и `C_out` делятся на `g`). Если групп столько же, сколько входных каналов (`g=C_in`), и каждой группе соответствует один выходной канал, получаем **depthwise-свёртку**: отдельный пространственный фильтр обрабатывает каждый входной канал, не смешивая значения разных каналов. Следующая свёртка `1×1`, называемая *pointwise*, на каждой позиции объединяет информацию из `C_in` каналов и формирует `C_out` выходных каналов. При одинаковых пространственных размерах выхода обоих этапов и одном выходном канале depthwise на каждый входной число MAC складывается из двух частей: `B·H_out·W_out·k_h·k_w·C_in` для depthwise и `B·H_out·W_out·C_in·C_out` для pointwise. В сумме получается

$$N_{MAC,sep}=B\,H_{out}W_{out}\bigl(k_hk_wC_{in}+C_{in}C_{out}\bigr).$$

Такое разделение применяется в семействе MobileNet [3](https://arxiv.org/abs/1704.04861). Рассмотрим расчётный пример: `B=1`, `H_out=W_out=128`, `k_h=k_w=3`, `C_in=32`, `C_out=64`. На выходе имеется `128·128=16 384` пространственные позиции. Для сравнения двух вариантов подсчитаем MAC по этапам:

- **Обычная свёртка:** в каждой позиции формируются `64` выходных канала, каждому требуются `3·3·32=288` MAC. Итого `16 384·64·288=301 989 888` MAC.
- **Depthwise:** каждый из `32` входных каналов обрабатывается своим фильтром `3×3`. Итого `16 384·32·9=4 718 592` MAC.
- **Pointwise:** в каждой позиции `64` выходных канала формируются из `32` каналов после depthwise. Итого `16 384·32·64=33 554 432` MAC.

Два последних этапа вместе требуют `4 718 592+33 554 432=38 273 024` MAC — приблизительно в `7,89` раза меньше, чем обычная свёртка для тех же размеров выхода. Это отношение относится к **числу арифметических операций**. Время обработки кадра дополнительно зависит от чтения и записи промежуточных карт, запуска двух этапов и распределения операций между CPU и ускорителем; его определяют экспериментально.

**Как тензоры приводят к рамкам лиц.** В детекторе свёрточные блоки преобразуют входное изображение в карты признаков; голова сети выдаёт оценки наличия объекта и параметры предполагаемых прямоугольников. На примере семейства SSD предсказания связывают с опорными прямоугольниками нескольких масштабов, после чего преобразуют координаты и подавляют повторяющиеся перекрывающиеся рамки [4](https://arxiv.org/abs/1512.02325). Конкретная TFLite-модель может содержать часть обработки рамок внутри графа, а часть — в программной постобработке: принадлежность операции к «модели» не гарантирует её исполнение на ускорителе. Под детекцией в работе понимается **локализация**, а не определение личности. Поэтому отдельные тензоры выходов и готовые рамки представляют разные стадии одной задачи; результат `invoke()` ещё не обязательно является окончательным результатом для кадра.

## 1.2 Анализ исполнения тензорных операций на CPU и специализированном ускорителе

Одна и та же формула может исполняться многими способами. CPU обрабатывает общий поток инструкций, а скорость матричных и свёрточных ядер зависит от векторизации, числа потоков, кэширования, раскладки и алгоритма библиотеки. Raspberry Pi 5 использует процессор BCM2712 с четырьмя ядрами Arm Cortex-A76 и многоуровневой кэш-памятью [10](https://github.com/raspberrypi/documentation/blob/7376533ab86ea07acc77ef6a9f3c3e57fcff833d/documentation/asciidoc/computers/processors/bcm2712.adoc). Современное исполнение на CPU также использует параллелизм: несколько ядер, векторные инструкции, кэширование и блочные алгоритмы. Поэтому сравнение с ускорителем проводится для оптимизированного вычислительного ядра, а не для учебного тройного цикла `i,j,k`.

Типичный специализированный тензорный вычислитель строится вокруг большого числа однотипных арифметических элементов, рассчитанных на повторяющиеся операции над матрицами и картами признаков. Идея *потока данных* состоит в том, что блоки входов и весов продвигаются между вычислительными элементами, многократно участвуя в MAC до обращения к более медленной памяти. Систолический массив — одна из известных архитектурных реализаций такого принципа. Работа Jouppi и соавторов [5](https://arxiv.org/abs/1704.04760) описывает TPU центра обработки данных и служит примером реализации потоковых вычислений. Особенности Edge TPU M.2 далее рассматриваются применительно к доступной документации Coral и наблюдаемым показателям выбранного стенда.

На используемой периферийной платформе вычисления выполняются как **гетерогенная система**: хостовая программа готовит кадр, взаимодействует с интерпретатором и получает выход; совместимые операции могут передаваться внешнему ускорителю; остальные операции и прикладная постобработка выполняются на CPU. Документация Raspberry Pi описывает внешний разъём PCIe Gen 2.0 ×1 у Pi 5 [11](https://github.com/raspberrypi/documentation/blob/7376533ab86ea07acc77ef6a9f3c3e57fcff833d/documentation/asciidoc/computers/raspberry-pi/pcie.adoc). Скорость обмена и задержку обработки для связки Pi 5, адаптера и Coral M.2 следует оценивать в условиях эксперимента с учётом драйвера, библиотеки, размеров тензоров и состава вычислительного графа.

Сопоставлять CPU и ускоритель корректно по **одной задаче**. Если CPU запускает float-модель, а Coral — другую INT8-модель, различаются одновременно устройство, численное представление и потенциально качество; скорость такого сравнения нельзя целиком приписать ускорителю. Основная пара — исходный квантованный TFLite-граф на CPU и соответствующий ему скомпилированный вариант для Coral на **той же** плате, с одинаковыми кадрами и пред-/постобработкой. Перед опытом проверяют формы, типы и смысл входных/выходных тензоров, версии рантайма, число потоков CPU, совпадение порогов и результат детекции. Ускоритель не заменяет CPU: даже при полном делегировании нейросети приложение инициализирует модель и формирует готовые рамки на хосте.

| Характеристика | Исполнение на CPU | Делегирование на Coral M.2 |
|---|---|---|
| Поддерживаемые задачи | Определяются ядрами интерпретатора и библиотекой; гибкость выше | Ограничены поддерживаемым набором операций и компиляцией графа [8](https://coral.ai/docs/edgetpu/models-intro/) |
| Организация параллелизма | Несколько ядер, векторизация, кэш, блочная обработка | Специализированные параллельные вычисления для совместимой части графа |
| Возможные накладные расходы | Вызов интерпретатора, чтение/запись данных, управление потоками | То же на хосте плюс взаимодействие с делегатом и устройством, возможное исполнение остатка графа на CPU |
| Что нужно измерять | Задержку стадии и полного пути, качество | Те же показатели **на той же плате**; дополнительно — доступный отчёт о делегировании |

Таблица систематизирует факторы, влияющие на задержку каждой конфигурации. Их количественный вклад оценивается по времени обработки одинаковых кадров и качеству детекции.

## 1.3 Анализ повторного использования данных, иерархии памяти и операционной интенсивности

**Зачем нужна локальность.** В формуле `Y=AV` один элемент матрицы `A` используется при вычислении нескольких столбцов `Y`, а один элемент `V` — нескольких строк. Если каждый MAC выполнять как две независимые загрузки из внешней памяти, для `M·N·K` MAC потребовалось бы до `2MNK` чтений входных элементов без учёта записи выходов. Это предельный расчёт для схемы без повторного использования данных; кэш и регистры CPU уменьшают фактический трафик на выбранном уровне памяти. Эффективное исполнение и на CPU, и на специализированном устройстве стремится удержать нужные данные ближе к вычислителю.

Вычислим блок результата размера `T_M×T_N` при длине сокращаемого измерения `T_K`. Для него требуется `T_M·T_N·T_K` MAC. Если блоки `A[T_M,T_K]` и `V[T_K,T_N]` удаётся однократно поместить в быструю память и накопить выход локально, достаточно загрузить порядка `T_M T_K + T_K T_N` входных элементов и записать `T_M T_N` элементов выхода. В идеализированной модели без такого повторного использования получилось бы `2 T_M T_N T_K` загрузок. Отсюда следует возможный выигрыш в **числе обращений на выбранной границе памяти**, но не во времени сам по себе: слишком большой блок не помещается в кэш, блок на границе матрицы бывает неполным, а при последовательных блоках по `K` частичные суммы могут потребовать дополнительных чтений и записей.

Для свёртки пространственная локальность означает, что соседние выходные позиции используют перекрывающиеся участки входного изображения. Вес одного фильтра используется для многих позиций изображения; пиксель участвует в нескольких соседних окнах. Алгоритм `im2col` превращает окна в матрицу и затем выполняет GEMM, что открывает доступ к оптимизированному матричному ядру, но явное разворачивание может размножить элементы в памяти. Прямая или блочная свёртка избегает полной материализации, однако её реальные перемещения данных зависят от реализованного ядра. Нельзя утверждать, что любая свёртка физически исполняется как полная матрица `im2col`, или выводить объём трафика из одной формулы MAC.

**Операционная интенсивность** `I=O/Q` — число арифметических операций `O`, делённое на объём передач `Q` в байтах **через указанную границу**: например, между оперативной памятью и кэшем CPU, между оперативной памятью и внешним устройством либо внутри самого ускорителя. Значения, вычисленные для разных границ, не взаимозаменяемы. В рамках одного блока GEMM при однократной загрузке двух входов и однократной записи результата можно оценить

$$I_{tile}\approx\frac{2T_MT_NT_K}{b_A T_MT_K+b_V T_KT_N+b_YT_MT_N}\quad\text{операций/байт},$$

где `b_A`, `b_V`, `b_Y` — число байтов на элемент соответствующего тензора. Формула относится к **идеальному блоку**, изначально с нулевым выходом; при нескольких блоках накопления понадобятся дополнительные передачи. В частности, для `T_M=T_N=T_K=64`, однобайтовых входов и четырёхбайтового результата верхняя иллюстративная оценка интенсивности равна `524 288 / 24 576 ≈ 21,3` операций/байт. При 32-битных входах и результате та же идеализация даёт `524 288 / 49 152 ≈ 10,7` операций/байт. Эти расчётные отношения характеризуют выбранную блочную схему и используются для анализа влияния формата данных. Оценка интенсивности Coral требует сведений о трафике на конкретной границе памяти; сравнение задержек INT8 и FP32 дополнительно учитывает состав арифметических устройств и формат результата.

Модель **Roofline** устанавливает верхнюю оценку достижимой производительности для конкретного вычислителя и конкретной границы памяти [1](https://dl.acm.org/doi/10.1145/1498765.1498785). Пусть `P_max` — предельная скорость арифметики в операциях/с, `B_mem` — пропускная способность памяти в байтах/с. Тогда

$$P_{achievable}\leq\min(P_{max},\ B_{mem}I),\qquad T_{kernel}\geq\max(O/P_{max},\ Q/B_{mem}).$$

Если `I < P_max/B_mem`, граница модели задаётся передачами; при большей интенсивности — арифметикой. «Точка перегиба» зависит от устройства и **измеряемого уровня памяти**. Практическая производительность может быть ниже обеих оценок из-за неполной загрузки ядер, зависимостей и служебных расходов. Прогноз по модели Roofline строится на согласованных значениях `P_max`, `B_mem` и `Q`, относящихся к одному устройству и выбранной границе памяти.

Для PCIe-ускорителя дополнительная граница — передача данных между памятью хоста и устройством. Если требуется передать `D` байтов при эффективной пропускной способности `B_link`, нижняя оценка времени передачи составляет `T_link ≥ D/B_link`; организация запросов и задержка их запуска увеличивают итоговое время. Фактический объём передач зависит от представления тензоров и работы драйвера, включая возможные преобразования данных. Паспортная полоса PCIe Gen 2.0 ×1 характеризует возможности канала, тогда как устойчивую скорость приложения определяют также размеры запросов и программная реализация. Часть обмена может входить в измеряемое время `invoke()`, поэтому при разложении задержки каждую составляющую учитывают однократно. Модель Roofline описывает ресурсные ограничения, а задержку полного пути определяют по границам прикладного конвейера.

## 1.4 Анализ делегирования операторов вычислительного графа и целочисленного квантования (INT8)

**Квантование чисел и тензоров.** Вещественные веса и активации модели можно приближённо представить целыми числами с масштабом `s>0` и нулевой точкой `z`. Для одного значения используется аффинное отображение

$$q=\operatorname{clip}\!\left(\operatorname{round}(x/s)+z,\ q_{min},q_{max}\right),\qquad \hat x=s(q-z).$$

`clip` ограничивает допустимый диапазон, `round` округляет по правилам реализации, `x̂` — восстановленное приближение. Например, при `x=0,37`, `s=0,03`, `z=−3` получаем `q=9` и `x̂=0,36`; ошибка `0,01` — результат **расчётного** примера. Для значений внутри диапазона ошибка одного округления не превосходит половины шага `s` при округлении к ближайшему, но за его пределами насыщение может дать гораздо большую ошибку. На выходе многих слоёв такие ошибки могут накапливаться; оценивать сохранение качества нужно по размеченным кадрам, а не только по разности пары чисел.

Спецификация 8-битного TensorFlow Lite различает **симметричные веса** `int8` с `z=0` (обычно диапазон `−127…127`) и **активации** `int8`, допускающие ненулевую точку (`−128…127`); весам свёртки могут соответствовать отдельные масштабы для выходных каналов, а смещения обычно накапливаются в более широком целочисленном формате [7](https://github.com/tensorflow/tensorflow/blob/a63268d6c0f5ae4e6ce397a8fa1b780d84573c47/tensorflow/lite/g3doc/performance/quantization_spec.md). У конкретных готовых моделей нужно проверить фактические типы входов/выходов: старые или смешанные варианты могут использовать `uint8` либо преобразования на границе графа. Деление значения на `s` при подготовке модели не означает, что аппаратно каждый MAC содержит деление: интерпретатор работает с целыми кодами, после накопления выполняется приведение к масштабу выхода.

При одном масштабе входа `s_x` и отдельном масштабе весов `s_{w,o}` для канала `o` произведение представляется приближённо как `xw ≈ s_x s_{w,o}(q_x−z_x) q_w`. Сумму произведений накапливают в более широком типе, затем с учётом смещения и масштаба выхода преобразуют обратно в код выходного тензора. Выбор масштаба **по каналам** позволяет лучше сохранить распределения весов, чем один масштаб для всего тензора, но не делает квантование безошибочным. В исследовании контраст `CPU INT8 ↔ TPU INT8` предназначен для оценки изменения способа исполнения при сопоставимой численной модели; контраст `CPU float ↔ CPU INT8` — отдельный вопрос о квантовании, возможный лишь при наличии сопоставимых весов и подготовки модели. Раздельный анализ этих контрастов позволяет выделить вклад смены численного представления и вклад смены исполнителя. Метод целочисленного инференса и способы сохранения точности обсуждаются в работе Jacob и соавторов [6](https://arxiv.org/abs/1712.05877).

**Граф операций и граница делегирования.** Нейросеть — направленный граф: узлы выполняют операции над тензорами, рёбра несут промежуточные массивы. Компилятор для Coral анализирует этот граф, параметры и типы тензоров и формирует совместимую часть для Edge TPU. Согласно документации Coral, для полного использования устройства требуются совместимые операции, фиксированные на этапе компиляции размеры и 8-битные квантованные параметры; неподдерживаемая часть остаётся на CPU [8](https://coral.ai/docs/edgetpu/models-intro/). В описанной версии компилятора поддерживаемый префикс до первого неподдерживаемого оператора заменяется одной пользовательской операцией, а остаток графа выполняется на CPU. Порядок разбиения графа для используемой версии устанавливается по отчёту компилятора.

Это означает, что даже небольшая по числу узлов неделегированная часть может влиять на задержку сильнее, чем многочисленные быстрые свёртки. В частности, поиск и фильтрация рамок, преобразование форматов или иные операции в конце модели могут выполняться на хосте. Число делегированных узлов описывает структуру графа, тогда как их вклад в задержку зависит от вычислительной стоимости: один узел обрабатывает большой тензор, другой — маленький. Отчёт компилятора фиксирует доступный состав делегированного графа, а время отдельных элементов закрытого чипа требует специальных средств профилирования. При использовании готовой `_edgetpu.tflite` версии модели и компилятора документируют отдельно: повторная компиляция другой версией может дать иной отчёт.

В API PyCoral [9](https://github.com/google-coral/pycoral/blob/46f06c8dd9c5231e5cb27910d4e1fcbdcf1be8f0/pycoral/utils/edgetpu.py) функция `make_interpreter()` создаёт TFLite-интерпретатор с Edge TPU-делегатом; один и тот же вызов `invoke()` охватывает взаимодействие с хостом, делегирование и возможный CPU fallback. Величина `T_invoke` поэтому характеризует вызов интерпретатора целиком; выделение времени работы кристалла требует отдельного профилирования. В используемой версии `make_interpreter()` параметр `num_threads` для управления CPU fallback отсутствует; при сравнении фиксируют число потоков CPU-контроля и особенности исполнения остатка графа. Для парных файлов из официального набора Coral [14](https://github.com/google-coral/test_data/tree/104342d2d3480b3e66203073dac24f4e2dbb4c41) перед экспериментом сверяют входы, выходы и состав делегированного графа.

## 1.5 Анализ модели задержки и предела ускорения

**Граница полной задачи.** Основной исход исследования — время от **декодированного кадра** до готовых рамок, полученных при фиксированных порогах. Для последовательной реализации без перекрытия стадий время кадра записывается так:

$$T_{frame}=T_{pre}+T_{set}+T_{invoke}+T_{get}+T_{post}.$$

`T_pre` включает преобразование цвета, масштабирование и подготовку входного тензора; `T_set` — передачу подготовленного массива через API интерпретатора; `T_invoke` — выполнение модели с внутренними накладными расходами вызова; `T_get` — чтение доступных выходов; `T_post` — перевод выходов в рамки и фильтрацию. Камера, декодирование и передача изображения по сети **не входят** в данную границу и при необходимости исследуются отдельно. Если часть операций выполняется асинхронно или стадии перекрываются, простая сумма времён отдельных вызовов перестаёт описывать задержку всего конвейера; тогда следует измерять его границы непосредственно. Даже при последовательном выполнении сумма **медиан** стадий вообще не равна медиане суммы времён для каждого кадра.

В режиме с ускорителем вызов `invoke()` объединяет работу делегата, подготовку и перемещение данных, выполнение совместимых операций и остатка графа на CPU. Программно наблюдаются времена `set/invoke/get` на хосте; выделение внутренних компонентов `invoke()` требует отдельного профилирования. Пиковые TOPS характеризуют арифметические возможности устройства, а `T_frame` дополнительно включает подготовку изображения и формирование рамок.

Пусть исходная задержка на CPU равна `T_CPU`, доля времени *реально ускоряемой части* равна `p` (`0≤p≤1`), её ускорение — `a>1`, а добавленные издержки делегирования относительно исходного времени — `δ`. При неизменности остальной работы и отсутствии двойного учёта издержек адаптированная форма закона Амдала [2](https://dl.acm.org/doi/10.1145/1465482.1465560) даёт

$$S_{frame}=\frac{T_{CPU}}{T_{TPU}}\approx\frac{1}{(1-p)+p/a+\delta}.$$

При `a→∞` предельное ускорение `S_max=1/(1−p+δ)`; если `δ=0`, остаётся классическая граница `1/(1−p)`. Условие `S_frame>1` при этих допущениях эквивалентно `p(1−1/a)>δ`: сэкономленное время должно превышать дополнительные расходы. В расчётном примере при `p=0,6`, `a=10`, `δ=0,05` итоговое ускорение равно `1/(0,4+0,06+0,05)≈1,96` при десятикратном ускорении выбранной части работы. Для применения модели к исследуемому стенду параметры или их допустимые диапазоны определяются экспериментально; одна пара измерений полной задержки позволяет оценить только их совокупный эффект.

Для сопоставления режимов вводятся `S_invoke=median(T_invoke,CPU)/median(T_invoke,TPU)` и `S_frame=median(T_frame,CPU)/median(T_frame,TPU)` **по одним и тем же входам**. Первое число характеризует вызов интерпретатора с видимыми программе накладными расходами, второе — прикладной результат. Если длительность остальных стадий одинакова в обоих режимах, положительна и постоянна для рассматриваемого кадра, то эффект ускорения `invoke()` на уровне полного пути уменьшается. При изменении затрат между кадрами отношения **медиан** оцениваются на парных данных с контролем версии постобработки и состава графа. Для зависимых кадров учитываются независимые сессии/сцены; `p95` характеризует хвост распределения времени и оценивается отдельно. Значение `1000/T_invoke` при `T_invoke` в миллисекундах характеризует частоту последовательных вызовов модели; производительность видеопотока оценивается отдельно с учётом стадий получения и обработки кадров.

Критерий применимости ускорителя предполагает одновременно: (а) `T_frame,TPU` меньше `T_frame,CPU` в сопоставимых условиях; (б) заранее установленное требование к задержке выполняется; (в) качество детекции не выходит за заранее определённый допустимый предел. Последнее проверяется по размеченным кадрам, например по AP при `IoU≥0,5`, полноте и ложным срабатываниям; совпадение одного тензора на нескольких изображениях не заменяет эту оценку. Экономическая часть сопоставит измеренное изменение задержки с дополнительными **разовыми** затратами на Coral и адаптер. Энергетические показатели требуют прямого измерения мощности и в выбранный набор метрик исследования не входят.

## 1.6 Критический анализ исследований и постановка проверяемых гипотез

Теоретическую основу анализа составляют закон Амдала [2](https://dl.acm.org/doi/10.1145/1465482.1465560) и модель Roofline [1](https://dl.acm.org/doi/10.1145/1498765.1498785). Первый связывает итоговое ускорение с долей времени, приходящейся на ускоряемые операции; вторая сопоставляет арифметическую производительность с пропускной способностью **на заданной границе памяти**. Применительно к детекции лиц эти модели дополняются измерением стадий конвейера и учётом условий исполнения на выбранном стенде.

На архитектурном уровне работа Jouppi и соавторов [5](https://arxiv.org/abs/1704.04760) исследует TPU центра обработки данных и иллюстрирует принципы специализированных вычислений. Семейство MobileNets [3](https://arxiv.org/abs/1704.04861) демонстрирует применение depthwise/pointwise-свёрток в компактных сетях, SSD [4](https://arxiv.org/abs/1512.02325) описывает формирование детекций, а Jacob и соавторы [6](https://arxiv.org/abs/1712.05877) рассматривают целочисленный инференс. При сопоставлении CPU и Coral в настоящей работе учитываются одновременно вычислительный граф, численное представление модели и качество детекции на размеченных изображениях.

Прикладные исследования задают основу для выбора условий эксперимента. Minott, Siddiqui и Haddad сравнивают edge-платформы, включая Raspberry Pi 5 с Coral, на задаче детекции объектов YOLOv5 [12](https://digitalcommons.georgiasouthern.edu/electrical-eng-facpubs/178/). Alqahtani и соавторы исследуют несколько семейств детекторов и платформ, включая Pi 5 с **Coral USB**, и сопоставляют время инференса и качество на COCO [13](https://arxiv.org/html/2409.16808v2). В части рассмотренных ими вариантов различается разрешение входа, что подчёркивает значимость согласованных условий сравнения. В настоящей работе исследуется парное исполнение сопоставимых INT8-вариантов на одном Pi 5 с **PCIe Coral M.2**, с одинаковыми кадрами, измерением времени от декодированного изображения до готовых рамок и оценкой качества детекции лиц. Такое сочетание условий позволяет связать делегирование графа с задержкой прикладного конвейера для выбранной конфигурации.

На основании анализа сформулированы **проверяемые гипотезы**:

1. **H1 (задержка вызова).** Для квантованных моделей с достаточным объёмом совместимых вычислений `median(T_invoke,CPU)>median(T_invoke,TPU)` на одном Pi 5 при одинаковых входах; величина различия зависит от размера модели и состава делегированного графа.
2. **H2 (полный конвейер).** При ускорении вызова модели (`S_invoke>1`) и одинаковой ненулевой задержке обработки вне модели в двух режимах ожидается `S_frame<S_invoke`; раздельный хронометраж стадий позволяет проверить выполнение этого условия для каждого варианта реализации.
3. **H3 (объяснение различий).** Оценку MAC и заявленные TOPS дополняют характеристики тензоров, движения данных, делегирования и затрат на хосте; совместный анализ этих факторов объясняет различия задержки для выбранного набора моделей.

Проверка H1–H3 проводится при заранее установленных границах времени и условиях опыта из раздела 2. Для сопоставления фиксируются входы, версия квантованной модели, число потоков CPU и особенности исполнения остатка графа; допустимое изменение метрик качества задаётся до анализа результатов. Научная задача состоит в экспериментальном определении и объяснении границ ускорения полного конвейера для выбранной задачи и оборудования.

## 1.7 Выводы по разделу

1. Тензорные операции нейросетей сводятся к обработке многомерных массивов: матричные произведения, свёртки и преобразования формируют разные по структуре нагрузки. Число MAC задаёт масштаб арифметики; для прогноза задержки его дополняют сведениями о памяти, формате тензоров и графе операций.
2. Повторное использование данных и блочная обработка повышают эффективность исполнения на CPU и специализированных устройствах. Модель Roofline задаёт верхнюю границу производительности для выбранного вычислителя и **конкретного** уровня памяти.
3. INT8-квантование уменьшает размер представления, но способно изменить выходы. Для оценки вклада ускорителя нужно сравнивать сопоставимые квантованные варианты на одной плате и отдельно проверять качество и реально делегированные операции.
4. Полный путь детекции лиц включает стадии на CPU даже при делегировании модели. Закон Амдала с учётом накладных расходов объясняет различие между ускорением `invoke()` и ускорением обработки кадра до получения рамок. Аналитические зависимости раздела задают основу измерений полного конвейера.
5. Предмет экспериментальной проверки — границы ускорения для выбранной **PCIe**-конфигурации, модели детекции лиц и одинаковых входных данных. В разделе 2 предусмотрены разработка инструмента, измерение задержки по стадиям и оценка качества детекции.
